# ZTmusic 全局 UI 设计规范

> 本文总结当前代码中的实际 UI 体系，用于设计评审、页面新增和样式维护。若文档与运行效果不一致，以 `src/App.svelte`、组件结构和 `src/main.js` 的全局样式加载顺序为准。

## 1. 产品气质

ZTmusic（哲听）的界面目标是“安静、专注、轻量的桌面音乐播放器”，视觉上吸收 Apple Music 的内容组织方式，但保留网易云音乐的红色品牌识别。

设计时遵守以下原则：

1. **音乐优先**：封面、歌曲名、歌手和播放状态高于装饰元素。
2. **低噪声**：默认界面以中性色、留白和轻边框组织层级，不堆叠高对比卡片。
3. **少而明确**：一个区域只保留一个主操作，次级动作降为图标、文字按钮或上下文菜单。
4. **状态可见**：加载、空结果、失败、禁用、当前播放和选中状态不能只靠用户猜测。
5. **跨端同语义、不同布局**：PC 与移动端共享内容和行为语义，但不强求同一排版。
6. **动效服务关系**：动效用于说明进入、切换、展开和播放状态，不作为持续装饰。

## 2. 界面结构

### 2.1 全局层级

```text
App
├─ 主应用层
│  ├─ PC：Sidebar + MainArea
│  └─ Mobile：MobileApp + Drawer + Bottom Tabs
├─ 常驻播放层：PlayerBar
├─ 沉浸播放层：LyricsPageV2 / AppleMusicPlayer
├─ 功能浮层：SearchOverlay / QueuePanel / LoginOverlay
├─ 对话层：ConfirmDialog / FollowDialog / 页面内 Dialog
└─ 全局反馈层：Toast
```

主要装配位置：

- `src/App.svelte`：运行时布局、页面切换、播放器和全局浮层。
- `src/lib/components/MobileApp.svelte`：移动端主导航、内容缓存、抽屉和详情页。
- `src/lib/stores/router.svelte.js`：基于 `activeView` 的视图切换；项目不使用客户端路由库。

### 2.2 PC 布局

PC 使用“侧栏 + 主内容 + 底部悬浮播放器”的三段结构：

| 区域 | 作用 | 关键实现 |
|---|---|---|
| Sidebar | 一级导航、账户入口、主题与资料库入口 | `Sidebar.svelte`、`.sidebar` |
| MainArea | 页面内容容器，内部独立滚动 | `App.svelte`、`.main-area`、`.content-scroll` |
| PlayerBar | 常驻播放信息、控制、音量和队列入口 | `PlayerBar.svelte`、`.player-bar-wrap` |

侧栏标准宽度为 `260px`，折叠宽度为 `68px`。主内容和侧栏使用独立表面与圆角分隔，播放器浮在主内容底部，不参与页面正常文档流。

### 2.3 移动端布局

移动端由 `html.mobile-runtime` 门控，不单纯依赖窗口宽度：

```text
MobileApp
├─ 左上头像入口
├─ 可滚动内容区 .m-content
├─ 四个主入口：首页 / 发现 / 歌单 / 搜索
├─ 侧滑抽屉 .m-drawer
└─ 底部悬浮 PlayerBar
```

移动布局约束：

- 使用 `100dvh`，处理移动浏览器动态视口。
- 顶部、底部和横屏布局必须计入 `env(safe-area-inset-*)`。
- 主标签页首次访问后常驻 DOM，切换时用 `inert` 和 `aria-hidden` 隔离，并恢复各标签滚动位置。
- 详情页隐藏底部主导航，返回动作由详情页头部或系统返回手势承担。
- 向下浏览时可收起底部导航，为内容和播放器让出空间。

## 3. 视觉令牌

全局令牌定义在 `src/app.css` 的 `:root` 和 `[data-theme="dark"]`。新增公共组件应优先使用令牌，不直接写主题相关颜色。

### 3.1 颜色

| 语义 | 令牌 | 用途 |
|---|---|---|
| 应用背景 | `--bg` | 最底层窗口背景 |
| 主表面 | `--bg-surface` | 侧栏、浮层、面板 |
| 次级层 | `--bg-layer` | 输入框、卡片、局部分组 |
| 高层表面 | `--bg-elevated` | 悬浮播放器、移动底栏 |
| 悬停/按下 | `--bg-hover` / `--bg-active` | 交互状态 |
| 主文字 | `--text` | 标题和主要信息 |
| 次级文字 | `--text-secondary` | 歌手、说明 |
| 弱文字 | `--text-tertiary` | 时长、辅助元数据 |
| 禁用文字 | `--text-disabled` | 不可用状态 |
| 品牌强调 | `--accent` | 当前项、主操作、链接 |
| 强调背景 | `--accent-bg` | 低强度选中态 |
| 危险操作 | `--danger` | 删除、取消收藏等不可逆倾向操作 |

浅色主题使用偏冷灰表面和深灰文字；深色主题使用近黑背景、分层灰表面与较亮的红色强调。播放按钮和进度可使用 `--accent-gradient`，普通导航和正文链接保持纯色强调。

### 3.2 圆角、边框与阴影

圆角采用有限的语义层级，禁止按单个页面随意微调：

| 令牌 | 数值 | 使用场景 |
|---|---:|---|
| `--radius-xs` | `6px` | 极小封面、提示块、紧凑控件 |
| `--radius-sm` | `8px` | 输入框、小按钮、小尺寸封面 |
| `--radius-md` | `12px` | 列表行、普通控件、中尺寸封面 |
| `--radius-lg` | `16px` | 卡片、对话框、悬浮 PlayerBar |
| `--radius-xl` | `20px` | Hero、全屏表面、页面主容器 |

使用规则：

- 同类、同层级组件必须使用同一令牌，不能出现 `10px`、`14px`、`18px`、`22px` 等游离值。
- 嵌套表面的圆角从外向内递减，通常相差一级；子元素圆角不得大于父容器。
- `999px` 只用于确实需要胶囊轮廓的标签、开关、短操作按钮和细长轨道；普通长条容器不能借此变成胶囊。
- `50%` 只用于宽高相等的头像、播放控制和圆形装饰。
- `0` / `inherit` 用于贴边表面和继承父容器；`1–4px` 只允许滚动条、进度轨等微型几何。
- 非对称圆角也必须由令牌组合，例如 `var(--radius-lg) var(--radius-lg) 0 0`。

`src/lib/utils/border-radius.test.js` 会扫描全局 CSS、Svelte 内联样式和运行时样式，阻止任意圆角值重新进入项目。

层级表达顺序为：背景差异 → 轻边框 → 阴影。不要让每个列表项同时拥有独立边框和重阴影。

阴影从 `--shadow-sm` 到 `--shadow-xl` 逐级使用：普通卡片用 `sm/md`，浮动播放器和对话框用 `lg/xl`。深色主题阴影更重，但边框更弱。

### 3.3 字体与字重

主字体是随包分发的 HarmonyOS Sans SC，回退到系统中文与 UI 字体。只允许三档真实字重：

| 字重 | 用途 |
|---|---|
| 400 | 正文、辅助信息、输入内容 |
| 500 | 按钮、列表标题、次级强调 |
| 700 | 页面标题、区块标题、歌曲主标题 |

禁止新增其他 `font-weight`，避免浏览器合成假粗体。`src/lib/utils/font-weight.test.js` 会检查该约束。

字号层级建议：

- 10–12px：标签、时间、计数、弱元数据。
- 13–15px：正文、列表和普通按钮。
- 16–19px：区块标题、输入框、强调内容。
- 20–32px：页面标题、当前歌曲标题。
- 更大字号只用于沉浸播放器和页面 Hero。

大于等于 `22px` 的标题应使用轻微负字距；歌词正文为了长句可读性允许正字距。

## 4. 内容组件模式

### 4.1 页面头部

页面头部通常包含：弱化的 kicker、主标题、简短说明和一个主操作。详情页头部可改为“返回 + 封面 + 元数据 + 播放全部”。

规则：

- 主标题只出现一次，避免同屏多个同等级大标题。
- 操作区最多突出一个填充色主按钮。
- 背景图必须叠加渐变或遮罩，保证文字对比度。
- 页面内容加载失败时保留页面框架，只替换主体状态。

### 4.2 列表和歌曲行

歌曲行的稳定信息顺序为：

```text
[封面/序号] [歌曲名 + 歌手/专辑] [时长/操作]
```

- 歌曲名使用主文字色和 500 字重。
- 歌手、专辑、时长使用次级或弱文字色。
- 当前播放项使用强调色或低强度强调背景。
- PC 可显示时长和行内操作；窄屏优先隐藏时长，保留标题和歌手。
- 行本身应可点击，额外操作必须阻止事件冒泡。
- 长文本使用 `min-width: 0`、单行省略；歌词和详情正文除外。

### 4.3 卡片、网格和横向轨道

- 卡片用于封面驱动内容，如歌单、专辑、每日推荐。
- 同一区块内封面比例保持一致，音乐封面默认 `1:1`。
- 移动端推荐使用横向轨道 `.m-rail` 或双列网格，不强塞 PC 多列布局。
- Hover 只属于有鼠标环境；移动端使用轻微缩放或背景变化表达按下。
- 卡片标题最多两层信息：主标题 + 一行元数据。

### 4.4 按钮

按钮分为四类：

| 类型 | 表现 | 使用场景 |
|---|---|---|
| 主按钮 | 强调色或强调渐变、白字 | 播放全部、登录、确认创建 |
| 次按钮 | 表面色或弱边框 | 取消、筛选、辅助动作 |
| 图标按钮 | 圆形/方形点击区、无文字 | 返回、关闭、更多、收藏 |
| 危险按钮 | `--danger` | 删除、取消收藏、清理数据 |

图标按钮必须有 `aria-label`。移动端可点击区域尽量不小于 `40×40px`，主要播放控制应更大。

### 4.5 搜索

搜索有两种入口：独立 `SearchPage` 和全局 `SearchOverlay`。两者共享以下结构：

1. 输入框与清空动作。
2. 综合 / 歌曲 / 歌手 / 歌单分类。
3. 最佳匹配和分组预览。
4. 搜索中、空结果和错误状态。

分类栏是固定高度的非收缩区域，结果区单独滚动。不得让长结果列表压缩搜索头或分类按钮。

### 4.6 播放器

播放体验分三层：

| 层 | 组件 | 目标 |
|---|---|---|
| 常驻层 | `PlayerBar.svelte` | 快速查看、播放/暂停、切歌、队列 |
| 展开层 | `LyricsPageV2.svelte` | 封面、歌词、完整控制 |
| 细节层 | `AppleMusicPlayer.svelte` | 音质、主题、评论、相似歌单等二级面板 |

播放器设计要求：

- 播放/暂停始终是视觉中心。
- 进度条支持鼠标、触摸和键盘，并提供 slider ARIA 属性。
- 当前歌曲元数据和控制状态由同一个 `player` store 驱动，避免 UI 自己维护另一套播放状态。
- 移动端播放器与底栏、刘海和安全区一起计算位置，不使用固定魔法高度覆盖内容。
- 沉浸歌词页允许使用封面取色、模糊背景和更强动效，但文字对比度必须稳定。

## 5. 浮层与反馈

### 5.1 浮层层级

全局 z-index 令牌：

```text
Sidebar 50
Player 100
Overlay 200
Dialog 400
Toast 600
```

新增浮层优先复用这些层级，不随意写更大的数字。对话框打开后，背景内容应使用遮罩，并通过 `inert`、焦点管理或等价方式避免误操作。

### 5.2 状态反馈

每个异步内容区至少覆盖：

- **Loading**：骨架屏适合内容列表，Spinner 适合短等待或局部操作。
- **Empty**：说明为什么为空，并在有明确恢复路径时给出动作。
- **Error**：显示用户可理解的信息；可重试操作不要只记录日志。
- **Disabled**：降低视觉强度，同时设置原生 `disabled` 或 ARIA 状态。
- **Success/Failure**：跨页面或短时操作使用 Toast；需要用户决策时使用 Dialog。

## 6. 动效

全局动效令牌：

| 令牌 | 时长 | 用途 |
|---|---:|---|
| `--dur-fast` | 150ms | Hover、按下、颜色变化 |
| `--dur-base` | 200ms | 普通状态切换 |
| `--dur-slow` | 300ms | 面板、抽屉、页面进入 |
| `--dur-slower` | 550ms | 主题过渡、较大视觉变化 |

缓动优先使用 `--ease-out`、`--ease-in-out`、`--ease-emphasized` 和 `--ease-spring`。

规范：

- 进入动画以淡入和小距离位移为主。
- 按下反馈使用轻微缩放，不改变布局尺寸。
- 不对 `width/height/top/left` 做高频播放动画，优先使用 `transform/opacity`。
- 必须为持续动画和大幅位移动画提供 `prefers-reduced-motion: reduce` 降级。

## 7. 响应式与平台适配

### 7.1 运行时门控

`src/main.js` 静态加载：

```js
import './app.css'
import './styles/shell.css'
import './styles/search-overlay.css'
// ...其他功能域样式
import './app-pc.css'
import './app-mobile.css'
```

- `app.css`：令牌、重置、共享动画和原生壳基础。
- `styles/*.css`：按 shell、search-overlay、player-bar、home、library、content、explore、lyrics 分割的功能域样式；歌词子模块位于 `styles/lyrics/`。
- `app-pc.css`：`html:not(.mobile-runtime)` 下的 PC 播放器与布局覆盖。
- `app-mobile.css`：`html.mobile-runtime` 下的移动壳、导航、抽屉和底部播放器。
- `styles/mobile/*.css`：移动歌词、通用组件、资料库、设置和响应式适配。

`responsive` store 与启动同步逻辑负责给根元素设置 `mobile-runtime`，防止首屏布局闪烁。不要把静态 CSS 改回变量动态导入。

### 7.2 断点使用

运行时类型决定 PC/移动大结构，媒体查询只处理结构内部的空间变化，例如：

- PC 主内容在较窄宽度下减少列数和间距。
- 移动端在 `360px`、`428px` 附近调整网格。
- `orientation: landscape` 处理手机横屏播放器和安全区。

不要仅凭一个 `max-width` 同时维护两套完整应用外壳。

## 8. 无障碍底线

- 所有纯图标按钮提供中文 `aria-label`。
- 当前导航使用 `aria-current="page"`，开关使用 `aria-pressed`。
- 对话框使用 `role="dialog"`、`aria-modal="true"`，并管理初始焦点和关闭动作。
- 进度、音量等连续值控件使用 `role="slider"` 和 `aria-value*`。
- 键盘焦点使用全局 `:focus-visible` 强调环，不要无替代地移除 outline。
- 非活跃但常驻的移动标签页使用 `inert` 和 `aria-hidden`。
- 文字与背景不能只依赖透明度形成极低对比；状态不能只靠颜色区分。
- 尊重 `prefers-reduced-motion`，并保证关闭动效后功能完整。

## 9. 样式归属与维护规则

选择样式放置位置时按以下顺序判断：

1. 全局令牌、reset 和原生壳基础：`app.css`。
2. 跨组件功能域样式：`src/styles/` 对应文件。
3. 仅 PC 或移动运行时使用的结构：`app-pc.css` / `app-mobile.css`。
4. 只属于单个组件且不需要跨文件覆盖：组件 `<style>`。
5. 页面独有样式：页面组件 `<style>`，避免继续扩大全局选择器范围。

维护约束：

- 匹配周围命名，不另建平行设计系统。
- 主题色使用令牌；沉浸歌词背景等特殊场景可使用局部颜色。
- 避免动态拼接 class 名，CSS 清理脚本依赖静态字面量。
- flex 滚动布局中的固定头部、标签栏和操作栏应设置 `flex-shrink: 0`；真正滚动的内容区设置 `min-height: 0`。
- 新增大字号、字体或动画后运行现有 UI 自检。
- 清理 CSS 前先运行 `node scripts/find-dead-css.mjs` 和 `node scripts/prune-dead-css.mjs --dry`。

## 10. 新增或修改 UI 的检查清单

### 结构

- [ ] 信息层级是否只有一个视觉主角？
- [ ] PC、移动端和详情页返回路径是否都明确？
- [ ] 固定区域不会被 flex 压缩，滚动区域具有 `min-height: 0`？
- [ ] PlayerBar、底栏和安全区不会遮挡内容？

### 视觉

- [ ] 使用现有颜色、圆角、阴影和动效令牌？
- [ ] 字重只使用 400 / 500 / 700？
- [ ] 长标题、歌手名和专辑名具有明确截断策略？
- [ ] 深色和浅色主题均有足够对比度？

### 交互

- [ ] Hover、Active、Focus、Disabled 状态完整？
- [ ] 点击行内按钮不会误触发行本身？
- [ ] Loading、Empty、Error 状态完整？
- [ ] 动画关闭后仍可使用？

### 无障碍

- [ ] 图标按钮具有 `aria-label`？
- [ ] 弹窗有语义、焦点管理和 Escape/返回关闭路径？
- [ ] 键盘可以操作主要控件？
- [ ] 选中和播放状态不只依赖颜色？

### 验证

```bash
pnpm test
pnpm build
```

至少人工检查：PC 浅色、PC 深色、窄屏移动端、带安全区设备、长中文标题、无封面、空结果、加载失败和 reduced-motion。

## 11. 当前已知维护点

以下是现状记录，不代表需要立即重构：

1. `styles/content.css` 仍包含一部分历史移动规则，新样式应放进明确归属的文件，避免继续交叉覆盖。
2. 部分老页面仍有各自的卡片、按钮和空状态写法；新增页面应优先复用本文的视觉语义，而不是复制整块旧 CSS。
3. `MobileApp.svelte` 当前渲染四个主入口；修改底栏时必须同时核对 DOM 数量、grid 列数和注释。
4. 全屏播放器同时存在 `PCPlayer`、`AppleMusicPlayer` 和共享控制组件，修改播放 UI 前先确认实际装配路径，避免只改到未使用的旧组件。
