## 1. 七项行为对照表

| 行为 | 宽屏路径 | 窄屏路径 | 共同实现 | 结果来源 | 结论 |
|---|---|---|---|---|---|
| **播放单曲** | 行点击 / Enter | 点按行 | `SongRow.onclick → onPlay → onPlayTrack(id, visibleTracks)` | 【结构】+【自动】`details-async`「filtered play all keeps playing only the visible subset」 | 逻辑一致 |
| **播放全部 / 随机** | Hero「播放全部」、工具栏 sticky 标题播放钮 | Hero「播放」、更多菜单 | 同一个 `onPlayAll(visibleTracks)` / `playShuffled()` | 【结构】 | 逻辑一致 |
| **搜索** | 工具栏常驻输入框 | 需先「更多 → 搜索与排序」展开 | `bind:search → filterAndSortPlaylistTracks`（只作用于已加载曲目） | 【结构】+【自动】`playlist-sort.test.ts` 13 checks | 能力一致，入口层级不同 |
| **排序** | 下拉 + 表头点击 + 方向按钮 | 排序按钮 → 底部弹层 | 同一个 `setSort()` / `trackSortDir` | 【结构】+【自动】同上 | 能力一致，形态不同 |
| **分享** | **无内容区入口** | 顶栏分享按钮 + Hero 更多菜单 | `sharePlaylist()`（共用函数） | 【结构】+【自动】守卫 | **两端不一致（见 §4.1）** |

## 3. 是否留下了两套完整列表实现

**没有。** 核对结果：

- 全仓只有 `src/lib/components/SongList.svelte`，只被 `PlaylistTrackTable.svelte` 引用；
- `SongRow.svelte` 只被 `SongList` 引用；
- 两个外壳渲染的是同一个 `pages/PlaylistPage.svelte`（`MobileApp.svelte:24`、`DesktopPageHost.svelte:56`）；
- 差异全部落在：外壳 chrome（顶栏 / 侧栏 / 底部 Tab）、`html.mobile-runtime` 下的 CSS、以及少量 `$responsive.isMobile` 的展示分支。

其他页面（搜索、喜欢、最近播放、歌手）仍各自持有 `<table class="track-table">`，那是**尚未推广**，不是「两端各留一套」。

## 4. 仍然存在的差异及原因

| # | 差异 | 原因 | 是否计划消除 |
|---|---|---|---|
| 1 | 宽屏没有「分享 / 更多」内容区入口 | C02 的约束是「保留现有可用操作」，没有新增桌面入口；顶栏只存在于窄屏 | 需要产品决策：是否在桌面 Hero 放开更多按钮（CSS 已就绪，删掉 `display:none` 即可） |

## 5. 必须人工执行的验收清单（**未执行**）

在 `node node_modules/vite/bin/vite.js`（或 `pnpm dev`）打开后，用同一张歌单各做一遍：

### 宽屏（≥ 1024px）
- [ ] 打开歌单 → 头部名称/封面/创建者/数量正确（歌单、专辑、推荐各一张）
- [ ] 点行播放：只播放该曲目，队列从该行开始
- [ ] 「播放全部」：队列为当前可见顺序
- [ ] 搜索：输入后列表过滤、光标不丢；清空后恢复
- [ ] 排序：四个表头 + 下拉 + 方向按钮都能改序
- [ ] 分页：滚到底加载下一页；观察 Network 无重复请求
- [ ] 分页失败（DevTools 断网）：已显示行仍在，底部出现重试；恢复网络后重试成功
- [ ] 返回：内容区返回栏回到来源页

### 窄屏（< 720px 或 `?mobile`）
- [ ] 上述播放/搜索（经「更多 → 搜索与排序」）/排序（弹层）/分页/返回 各做一遍
- [ ] 长按行打开菜单；滚动时不应误开；一次手势只开一个菜单
- [ ] Escape / 点击遮罩关闭菜单后，焦点回到该行
- [ ] 顶栏分享能拉起分享
- [ ] 空歌单显示「这个歌单还没有歌曲」；搜索无匹配显示「没有匹配的歌曲」或带已加载范围提示

### 两端之间
- [ ] 宽→窄→宽：搜索词、排序、已加载条数保持不变
- [ ] 切换布局不产生额外历史（按返回应回到进入歌单前的页面）
